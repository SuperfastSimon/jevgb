# Handoff contract: Grok Bot → Grok Build → Grok Bot

## Why

Forwarding a whole chat to a coding agent sends everything: old topics, repeated recaps, tool output. A structured brief sends only what the coding agent needs. Whether that saves tokens depends on how long the chat was. `jevgb report` measures it per task, including the cases where the brief costs more than a short chat would have.

## Flow

```text
Grok Bot ──route(state + history_path)──▶ JevGB
   ▲                                      │ action = handoff_build
   │                                      ▼
   │                         handoffs/<task_id>.md  (brief, ≤ max_brief_tokens)
   │                                      │ grok -p "$(cat handoffs/<task_id>.md)"
   │                                      ▼
   │                                 Grok Build (reads AGENTS.md, does the work)
   │                                      │ final message ends with ```build-result {json}```
   └──── jevgb result out.txt --task-id ◀───┘   → short relay text + ledger record
```

## Brief template

Generated by `jevgb/handoff.py`. Fields come from the router state. The chat history is summarized before the handoff, never forwarded raw.

```markdown
# Grok Build handoff <task_id>

## Goal
<one or two sentences>

## Repo
- path/url: <repo>
- branch: <branch, optional>

## Files in scope
- <path>

## Constraints
- <constraint>

## Acceptance criteria
- <testable criterion>            (default: existing tests pass; new behavior covered by a test)

## Do not touch
- <path or system>                (default: secrets/.env/credentials; git remote, pushes, releases)

## Context (summarized from chat; ask if something is missing)
- <lines with requirements, decisions, paths, errors, plus the latest user turns, within max_summary_tokens>

## Report back (required)
End your final message with exactly one fenced block tagged `build-result` containing JSON: {...}
```

### How the summary is built (deterministic, no LLM call)

1. Keep lines that contain requirement or decision cues (`must`, `don't`, `never`, `only`, `test`, `error`, `decided`, Dutch `moet`, `niet`, `nooit`, …) or file paths.
2. Always keep the last 3 lines (latest intent).
3. Drop near-duplicates (lines that differ only by numbers).
4. Stop when `max_summary_tokens` is reached. If the whole brief is still over `max_brief_tokens`, the summary is trimmed first; structured fields stay intact.

This is extractive and crude on purpose: it is free, predictable and testable. It can drop context that a human would keep. Grok Build is told to report `blocked` with `open_questions` rather than guess.

## Return contract

| field | type | notes |
| --- | --- | --- |
| `status` | `done \| partial \| blocked \| failed` | required |
| `summary` | string ≤ 600 chars | required |
| `files_changed` | string[] | paths only |
| `tests` | `{command, passed, failed}` | |
| `acceptance` | `[{criterion, met}]` | unmet items are surfaced in the relay |
| `open_questions` | string[] | |
| `needs_human` | bool | relay says a decision is needed |
| `next_step` | string | |

`jevgb result FILE` validates the block, prints a relay message, and with `--task-id` logs `build_result_relay`: baseline = tokens of the full Grok Build output, actual = tokens of the relay.

## What is measured, exactly

- `handoff_build`: baseline = tokens(history + goal), measured from `history_path` or inline history. Actual = tokens(brief). Without history, baseline = tokens(goal) and the record is marked `goal_only`. That usually shows a *negative* saving, on purpose.
- Grok Build's own exploration (reading files, running tests) is **not** measured. It happens either way.
